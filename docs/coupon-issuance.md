# 쿠폰 발급·직원 확인

## 운영 방법

1. 기존 관리자 로그인 후 관리자 메뉴의 **쿠폰 발급 관리** 또는 `/admin-coupons.html`을 연다.
2. 새 쿠폰 등록에서 쿠폰명, 사용 매장, 혜택 내용, 혜택 이미지, 한국 시간 기준 사용 시작·종료, 사용 안내, 총 발급 한도를 입력한다.
3. 필요하면 퍼니핀에 가입한 직원 계정을 이메일/닉네임으로 검색해 지정한다. 미지정 시 활성 관리자만 확인 가능하다.
4. 등록된 쿠폰을 선택하고 회원을 검색·선택한 뒤 발급 내용을 확인하여 지급한다. 한 요청 최대 100명, 같은 쿠폰은 회원당 1장이다.
5. 회원은 MY 쿠폰함에서 이미지·혜택·기간·안내를 확인한다. **직원 확인** 버튼은 확인용 코드를 보여주며 사용 처리를 요청하지 않는다.
6. 직원은 자신의 기기에서 퍼니핀 로그인 후 `/coupon-redemption.html`을 열고 고객 코드를 입력한다. 코드·상품·사용 가능 상태와 실물 교환을 확인한 다음 사용 확정한다.

직원 권한은 쿠폰별로 제한된다. **담당 직원 권한 관리**에서 즉시 회수·변경할 수 있다. 회원이 직원 권한을 가지고 있어도 자신의 쿠폰을 직접 소진할 수 없다. 관리자 계정을 매장 직원에게 공유하지 않는다. 이 방식은 지정 계정의 확인을 기록하며, 실제 매장 근무나 현장 존재 자체를 기술적으로 증명하지는 않는다.

## 정책

- `source_type=admin_coupon`만 새 흐름을 사용한다. 기존 일반 쿠폰과 더카드룸 `event_test` 쿠폰은 기존 표시·처리 정책을 유지한다.
- 혜택·사용 기간은 등록 후 고정된다. 이미 발급한 혜택이 바뀌지 않도록 발급 시 내용을 스냅샷으로 저장한다. 수정된 혜택은 새 쿠폰으로 등록한다.
- 총 발급 한도 1~10,000장, 요청당 1~100명, 담당 직원 최대 20명. 취소된 쿠폰도 누적 한도와 회원당 1장 제한에 포함된다.
- 신규 발급 중지는 이미 발급한 쿠폰의 사용을 막지 않는다. 개별 발급 취소는 미사용 쿠폰에만 적용하며 사유·처리자·시각을 기록한다.
- 발급 내역은 50건씩 조회하며, 등록된 쿠폰 목록은 최신 200개를 제공한다.
- 사용 시작 전·만료·취소·사용 완료 쿠폰은 사용 확정할 수 없다. DB 행 잠금과 상태 검사로 동시·중복 사용을 막는다.
- 중복 지급은 DB 고유 인덱스로 막고, 발급 수량 계산은 쿠폰 행 잠금 안에서 수행한다. 같은 대상 요청의 재시도는 이미 지급된 회원을 건너뛴다.
- 등록 요청 UUID와 내용을 저장해 응답 유실 후에도 동일 요청을 재시도할 수 있다. 미확인 발급 요청은 관리자 브라우저 sessionStorage에 유지하고 같은 대상으로만 다시 확인한다. DB가 명시적으로 거절한 요청은 수정할 수 있다.
- 이미지: JPG/PNG/WEBP, 최대 5MB, 4천만 화소 이하. 공개 혜택 이미지 전용 버킷에 관리자만 업로드한다. 발급 후 이미지가 바뀌지 않도록 객체 덮어쓰기·삭제 권한은 주지 않는다.
- 고객 쿠폰 metadata에는 담당 직원 목록·계정 이메일을 포함하지 않는다. 발급·사용 처리자의 UUID와 시각은 감사 정보로 기록한다. 관리자 이력 조회에서만 수령인 이메일·닉네임에 접근한다.
- 발급은 기존 쿠폰 알림 트리거를 사용한다. 실제 푸시 수신 여부는 이번 검증 범위에서 실기기로 확인하지 않았다.

## DB 및 접근 권한

`coupon_campaigns`는 RLS를 적용하고 활성 관리자만 조회한다. 클라이언트 직접 쓰기는 허용하지 않는다. 신규 발급/취소/권한 관리 RPC는 DB의 `is_funypin_admin()`으로 매번 인증한다. 직원 조회·사용 RPC는 해당 쿠폰에 지정된 계정 또는 활성 관리자만 허용하고, 탈퇴/이용 제한 계정은 거절한다. anon/PUBLIC 실행 권한은 제거했다. 기존 `user_coupons`의 본인 조회 RLS는 변경하지 않았다.

관리자 권한을 검사하는 공개 RPC는 SECURITY DEFINER이므로 Supabase advisor의 authenticated executable 경고가 발생할 수 있다. 운영상 의도된 API이며, 빈 search_path·명시적 스키마·서버 권한 검사·최소 반환 필드로 제한한다. 기존 프로젝트의 다른 advisor 경고는 이 변경에서 수정하지 않았다.

## 검증

- `tests/coupon-issuance.sql`: 정상/중복 발급, 등록 재시도, 한도, 소유자 RLS, 고객·익명 접근 거절, 지정 직원 정상/중복 사용, 본인 쿠폰 직접 사용 거절, 기간 제한, 발급 취소, 직원 권한 회수·변경 이력. 임시 쿠폰·이미지 메타데이터·알림 삽입을 내부 서브트랜잭션으로 모두 롤백하고 기존 쿠폰 해시가 같음을 확인한다. 실발급 쿠폰을 소진하지 않는다.
- `tests/coupon-browser.cjs`: 실제 HTML/JS를 Chromium에서 실행하고 HTTP 응답만 모의 처리한다. 이미지 업로드/등록, 회원 선택, 응답 유실·새로고침·동일 요청 재시도, 직원 권한 회수, 기존 일반 쿠폰 렌더링, 고객 읽기 전용 확인창, 사용 처리 응답 유실 후 상태 재조회, 모바일/PC 가로 넘침을 검증한다. 프로덕션 쿠폰을 실제 발급하거나 사용하지 않는다.
- 기존 `tests/test-cardroom-coupon.cjs` 회귀 검사 유지.

브라우저 테스트는 tests 의존성 설치 후 `npx playwright install chromium`, `node tests/coupon-browser.cjs`로 실행한다. 별도 Chromium 실행 파일을 쓸 때 `COUPON_BROWSER_EXECUTABLE`을 지정할 수 있다. `COUPON_QA_IMAGE`, `COUPON_QA_FONT_ROOT`는 로컬 시각 QA용 선택 옵션이며 제품 의존성이 아니다.

## 앱 적용

발급 데이터·권한·사용 처리는 공통 DB에 적용되므로 서버 변경에 앱 재빌드는 필요 없다. `/my-coupons.html`을 읽는 WebView는 새 파일을 로드하면 신규 디자인을 사용한다. 이 저장소에는 iOS/Android 네이티브 쿠폰 화면 소스가 없어 네이티브 화면의 이미지·버튼 및 실기기 적용은 확인하지 않았다. 자체 네이티브 화면이면 해당 앱 코드 변경과 재빌드가 별도로 필요하다.

## 롤백

웹 파일은 이 커밋의 변경만 되돌릴 수 있다. 운영 발급 이후에는 DB 테이블·인덱스·발급 이력을 삭제하지 않는다. 긴급 중단은 관리자에서 신규 발급을 중지하고 필요하면 담당 직원 권한을 회수한다. 이미 발급된 쿠폰 전체 사용을 중단해야 한다면 고객 안내와 별도의 운영 결정을 거친다.
